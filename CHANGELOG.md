# Changelog

All notable changes to this project are documented here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Reader observability** — `DbStats` gains `oldest_reader_commit_id`, `oldest_reader_age_ms` (both `None` when no reader is registered) and `tracked_readers_non_abortable` (`u32`), so a long-lived read transaction that holds back free-page reuse is visible from `Db::stats()`.
- **Compaction decline flag** — `CompactStats` and `CompactProgress` gain `declined_readers_pinned` (`bool`). `compact_now` and `compact_step` set it when a registered reader pins the page range and the pass does not run, so a caller can tell that result apart from a pass that found nothing to reclaim. Every count is zero in both cases, and `CompactProgress::more_work` stays `false`.

### Changed

- **First flush after an open** — the first flush of `main.db` pages after an open now writes a header first. The anchor it holds covers every page that flush seals. If that write fails, the flush returns the error and seals no page. Commit fault handling sees that error as a plain flush error. An open that only reads writes nothing.
- **Maximum anchor budget** — `OpenOptions::anchor_budget` now has a maximum of 1,048,576 (2^20). A larger value issues under the maximum. An open now skips the maximum on the nonce counter, whatever the option holds. So each open that writes a header spends 2^20 counter values. The 48-bit counter lasts 2^28 such opens before sealed pages are counted.
- **Follower page prefix** — a `Follower` handle now seals its own `main.db` pages under a random 6-byte nonce prefix drawn at each open or `promote_to_follower`. An open refuses a draw equal to the store's prefix. A match between two followers is improbable rather than impossible. The key and `file_identity` do not change, and delta pages keep the source's nonces. The on-disk format does not change, because a reader takes each page's nonce from its envelope. Pages sealed before this release keep their nonces.
- **New `RestoredNotPromoted` refusal for a byte copy** — the first `apply_incremental` on a copy of a store, made outside the API, now durably records the follower stamp before any delta page lands. Every later `Standalone` open of that copy reports `RestoredNotPromoted`. Before, the copy reopened as a writer. Its commits then repeated the source's nonces and mixed two counter streams. An apply refused by its manifest, its delta screen, or a pinned reader changes nothing. An apply that fails later keeps the stamp, with no delta page in `main.db`. `rekey_into_writer` forks a writer from such a copy. A copy opened as a follower with no apply keeps opening as `Standalone`. A copy that took an apply under an earlier release holds no stamp and still opens as `Standalone`.
- **Mode gates on two store writes** — `set_realm_quotas` now returns `WrongMode` on `Follower`, `ReadOnly`, and `Observer` handles. `gc_now` now returns `WrongMode` on `ReadOnly` and `Observer` handles.
- **MSRV is Rust 1.88** — earlier toolchains did not build, because the crate and `faultbox` use let-chains.
- **Visibility gate on metadata walks** — `Db::stats`, `list_segments`, `open_segment`, and `realm_quotas` hold the visibility gate for their walk. They wait during a compaction or an apply, and a commit's publication waits for them. `run_deep_walk` holds the writer lock for its whole walk. `page_provenance` with a busy writer reports the free list as an unwalkable gap.
- **Page cache invariant error** — new `PagedbError::PageCacheStateInvalid` replaces a panic when the page cache breaks an invariant. The cache latches the error, and every later operation on that cache reports it. Close and reopen the handle to clear it. No fault is known in the store files.
- **Free pages after a rekey** — a free page below the reclamation floor reads as a zeroed `Free` page on disk after a rekey.
- **Rekey disk use** — `rekey_db`, and an open that resumes one, now need free space up to the size of `main.db`, from the first write to `main.db.rekey` until its rename over `main.db`. On a full device `rekey_db` returns the new `PagedbError::RekeyNoSpace`, removes its scratch, withdraws its intent, and leaves the store as it was. An open with a pending rekey returns the same error, leaves `main.db` intact, and needs space before it can finish.
- **Handle after a failed or dropped rekey** — an error or a drop before the rename now leaves the handle usable under the source key, with `main.db` intact and no target key in the handle. A full device at the first intent write returns `RekeyNoSpace` too. The intent stays durable unless the device was full. Three things settle it: the next `rekey_db` with any target key, an open with both keys, or an open with the source key alone. That last open reads every page envelope. If no page is under the target key, it withdraws the intent, and the rekey never happened. A read-only open reads such a store. One target page, which only an earlier release's in-place write can leave, still returns `RekeyResumeKeyRequired`. `snapshot_to` and `snapshot_incremental_to` return the new `PagedbError::RekeyPending` until the intent settles, because a restored copy has no writer to settle it.
- **Keep both keys until a rekey returns** — past the rename, the store opens only with the target key, and a KEK-changing resume also needs the source key to move its segments. Losing the target key then loses the store.
- **Linking across a rekey** — `link_segment` and `replace_segment` now return the new `PagedbError::SegmentEpochStale`, before the row lands, for a segment sealed under an epoch other than the store's. Write the segment again. Before, the row named an epoch no later open holds, and every later open failed. A `SegmentWriter` now derives every key from the epoch it pinned at create. Once a rekey retires that epoch, it returns `MissingPersistedKey`.
- **Open beside a damaged segment** — a linked segment whose file fails to authenticate no longer fails the open. The file stays in place, the row stays in the catalog, and `open_segment` reports the damage, so `WriteTxn::unlink_segment` can quarantine it. Before, the open failed, and no handle existed to make that call. A foreign segment, a missing segment, a malformed row, and an I/O error still fail the open. `run_deep_walk` reports the damage.
- **Rekey beside a damaged segment** — `rekey_db` refuses a linked segment whose metadata fails to authenticate, before any write. Unlink it first. A data page that goes bad after that check leaves its row under the source epoch, and the rekey finishes. Reads of that segment then report `MissingPersistedKey`, and its file stays under the old key until an unlink.
- **Keys at an open after a rekey's rename** — `main.db` then holds one header, under the target key. An open with only the source KEK of a KEK-changing rekey reports the header as unverifiable, not `RekeyResumeKeyRequired`, until the next header write. The source key and its counterpart still resume the rekey in either order.

### Fixed

- **Torn write during a rekey** — a rekey re-sealed live pages in place, so a torn write destroyed the only copy and every open that resumed the rekey failed. It now rebuilds `main.db` in a scratch file with the same page ids and renames it into place, with a directory sync. A crash before the rename leaves the old file whole, and the next open removes the scratch and starts over. A crash after it continues from the new file. The on-disk format and the stage values do not change. An intent an earlier release wrote before `MainDone` resumes through the same rebuild, with both keys in one file. A page that release already tore stays unrecoverable, and the open returns `Corruption`, as before.
- **Crash during an OPFS rename** — the OPFS worker renames by copying, and a crash mid-copy left a partial destination. A `main.db` then lost its only full copy when the open removed the scratch, or failed to open. A journal beside the destination now names the source. The next open, remove, or listing finishes the copy, so `rekey_db`, `compact_now`, `apply_incremental`, and segment renames end with one whole file or the other. An open that arrives during a rename now waits for it.
- **Pages left under the old key by a rekey** — pages no root, retained row, or free list named stayed under the source key after a rekey, so the old KEK still decrypted them. That covers crash leftovers past the cursor, a detached torn free chain and its entries, and older leaks. A rekey now copies none of them. They read as zeros, the file ends at the cursor, and the free list names each hole below the cursor. An intent an earlier release left at `MainDone` or later skips the rebuild, so that rekey keeps those pages until the next one.

- **Writes that outlive a dropped future** — on the `io_uring`, IOCP, `dispatch_io`, and thread-pool backends, a write, sync, truncate, or open on a file now waits for that file's in-flight writes in the process. Before, a dropped commit's stale pages could land after the next writer's flush at the same ids. The thread-pool `write_at` now returns once its bytes reach the OS, not when they are queued.
- **Unfinished `WriteTxn` mutations** — after a dropped `put`, `delete`, or other mutating future, or an I/O or corruption error from one, every read, mutation, and `commit` on that transaction returns the new `PagedbError::WriteTxnInterrupted`. Before, `commit` could publish a partly updated tree, or a free list holding a live page. Validation errors such as `AppendNotMonotonic`, `PayloadTooLarge`, `NotLinked`, and `Quota` keep the transaction usable. `put_batch` now validates every pair before it applies the first. Dropping or aborting the transaction stays a clean abort.
- **Failed header writes** — a failed write or sync of the header in `WriteTxn::commit`, `set_realm_quotas`, or a segment replacement during `compact_now` now poisons the handle with the new `PagedbError::CommitOutcomeUnknown`, which carries the cause as `source`. Before, the handle kept old state, although a failed sync can leave the new header durable. Reopen to learn the outcome. An encode or open failure writes no byte, so it returns its own error and the handle stays usable.
- **Pages leaked by `set_realm_quotas`** — each call now adds the catalog pages it supersedes to the free list.
- **Dropped apply between journal staging and flush** — dropping `apply_incremental` there now removes the dirty journal pages from the cache. Before, they held their cache budget until a reopen.
- **Dropped compact after its rename** — dropping `compact_now` or `compact_step` from the rename to publication now poisons the handle. Before, the published snapshot named old roots over the new file. Every later call returns `DurablyCommittedButUnpublished` until a reopen.
- **Dropped compact before its rename** — dropping `compact_now` or `compact_step` while it builds its scratch now removes the compacted pages from the cache. Before, later reads got compacted pages under source ids, and the next commit wrote the dirty ones over live pages. The handle stays usable.
- **Dropped commit** — dropping `WriteTxn::commit` from its header write to publication now poisons the handle. A drop before the header write stays a plain abort.
- **Dropped commit during spill cleanup** — the spill gauge now resets, and the next `begin_write` removes the spill file.
- **Dropped rekey** — dropping `rekey_db` during its first intent write, or from its rename on, now poisons the handle. A reopen resumes the rekey from the durable stage. A drop while it waits for the writer lock changes nothing. A drop during the rebuild between them, or at the visibility gate before the rename, leaves the handle usable.
- **Dropped incremental apply** — dropping `apply_incremental` from its rename to publication now poisons the handle. A drop before the rename removes its staged pages from the cache, and the same delta applies on retry.
- **Dropped segment repack** — dropping `compact_now` during a segment replacement now poisons the handle from the header write on. A drop before the header write discards the staged catalog pages.
- **Dropped `set_realm_quotas`** — a drop from the header write on now poisons the handle. A drop before it discards the staged catalog pages.
- **Dropped `gc_now`** — the deferred tombstones it had taken return to the queue. Before, their files stayed on disk until the next open.
- **Pages leaked by a segment repack** — `compact_now` now adds the catalog pages each segment replacement supersedes to the free list. The next `compact_now` therefore runs a repack.
- **Commit history lost by a segment repack** — a segment replacement wrote commit-history root 0 into the header when the main repack was skipped. A reopen then lost every retained commit.
- **Poison checks after a wait** — `begin_read`, `begin_read_non_abortable`, `begin_read_at`, `open_segment`, `list_segments`, `realm_quotas`, `gc_now`, `rekey_db`, `run_deep_walk`, and the apply-journal retry now check poison again after they get the lock or gate they wait for.
- **`stats` and `page_provenance` on a poisoned handle** — both now return `DurablyCommittedButUnpublished`. Before, they walked the published roots, which can name pages in a file they do not describe.
- **Pinned follower readers** — `apply_incremental` now returns `ApplyBlockedByPinnedReader`, before it changes `main.db`, when its delta rewrites a page a reader pinned before the base commit can reach. That reader previously read authenticated bytes from the later commit. Retry the same delta after the reader finishes.
- **Commit-history retention after a reopen** — with `RetainPolicy::Count(n)`, the first commit after a reopen pruned one commit too many and kept `n - 1`.
- **Relocated commit history on a small buffer pool** — an apply that relocated a commit-history tree larger than the buffer pool flushed part of it to the live `main.db`. The published image then lacked those pages.
- **Historical reads after a rekey** — `rekey_db` tagged the catalog pages it superseded with the latest commit, so a later commit recycled them while that commit's retained row still named them. `begin_read_at` then failed with `ChecksumFailure`. New entries carry the next commit id. Entries an earlier release left on a free list keep their old tag. On any rekeyed store (`mk_epoch > 0`), a row now holds back the pages tagged with its own commit, so reuse there runs one commit later. A store never rekeyed keeps its reuse timing. The on-disk format does not change.
- **`RetainPolicy::Disabled` with rows present** — a handle under it carried the old history root forward and served old commits, while the reclamation floor ignored them, so `begin_read_at` can read recycled pages. `begin_read_at` and `snapshot_incremental_to` now serve the latest commit only, and return `CommitGone` for any other. The first commit, `rekey_db`, or `apply_incremental` under `Disabled` frees the history tree and writes root zero. Those rows stay gone under any later policy. Until the removal is durable, the rows still hold back free-page reuse. Read-only and observer handles, including `pagedb-fsck`, change nothing and report no error for the rows.
- **Rows an earlier release abandoned** — a header holding the `Disabled` tag beside a non-zero history root proves those rows went unmaintained. `begin_read_at` reports `CommitGone` for them under every policy, and a writable handle removes them at its first write. An earlier release can also have overwritten that tag, and such rows remain undetectable.
- **Deep walk key choice** — `run_deep_walk` derived a page's key from the active master key whatever epoch the page named, and cached that cipher where reads find it. A page under a retained older epoch then failed its own read. It now uses the key the page names.
- **Stale retention tag** — a header written after a commit, such as by `set_realm_quotas`, `rekey_db`, or a segment repack, repeated the tag from open. It now repeats the tag of the last commit.
- **Torn free-list chain during a rekey resume** — an open now detaches an unreadable chain before it resumes a rekey. Before, a torn chain page failed the open. The resumed rekey copies none of the chain's pages, and the free list names their holes.
- **Legacy rekey intent** — an open now persists a missing target proof during the resume, after the mode check and the chain detach. Before, a torn chain page failed admission, and a read-only open attempted the write.
- **Export after a detached chain** — `snapshot_to` now succeeds on a store whose open detached a torn free-list chain. Before, it read the torn page and returned that error. The exported header names the published free-list root, so the copy does not name the torn chain.
- **Stale history row during a rekey** — `rekey_db` walked retained rows after its intent was durable, so one unreadable row failed the rekey and then every open that resumed it. `rekey_db` now walks them first, read-only. A row with a page that fails authentication, names no known cipher, names an epoch with no key, or lies past the end of the file leaves durably with every older row. `begin_read_at` reports `CommitGone` for them. A resume does the same, so an intent an earlier release wrote also recovers. Any other I/O error fails the rekey and prunes nothing. A resume with a key missing fails before it reads a row. If the history index itself cannot authenticate, every row leaves, and the rekey copies none of the index pages. Reading a page whose cipher byte names no cipher now returns `Corruption` with `PageUnverifiable`, not `Unsupported`. `apply_incremental` uses the same rule for a retained row, and `rekey_db` for a free page. An unreadable live page now fails `rekey_db` before it writes anything, and the store still opens. Each rekey reads every page it walks one extra time.
- **Historical reads on a follower** — `apply_incremental` carried commit-history rows whose pages its delta overwrote, so `begin_read_at` admitted a reader over bytes from a later commit. An apply now prunes the newest such row and every older row, durably, and `begin_read_at` reports `CommitGone` for them. Surviving rows read their own values. An apply on a follower with retained rows now reads each retained page the base does not reach once.
- **First delta after a catalog move** — `set_realm_quotas` and `rekey_db` move the catalog root under one commit id, and the retained row keeps the old root. A follower restored after the move holds the new catalog as live, and the export ships those pages as new. `apply_incremental` then returned `SnapshotBasePageReused`, so such a follower could not apply its first delta. A record naming a base-live page is now compared with the base image. Identical bytes write nothing and do not count in `ApplyStats::pages_applied`. Different bytes still return `SnapshotBasePageReused`. Applying such a delta costs one extra page read per matching record.
- **Delta from a commit a segment repack published** — a segment repack bumps the commit id and writes no row, so `snapshot_incremental_to` reported `CommitGone` for that base once a later commit landed. A follower on that commit could not advance. The next commit now writes the missing row first, when the store has a history tree. It counts toward the retention policy. A commit an earlier release already moved past stays without a row. A main repack resets the rows, so an export based on the commit it published still reports `CommitGone`. Restore a full snapshot in that case.
- **Delta from a rekeyed producer** — a follower from before a producer's `rekey_db` now gets `SnapshotIncompatible` naming `mk_epoch`. Before, it got `Corruption` naming `manifest.hk_mac`. Either way the apply changes nothing. Restore a full snapshot.
- **Older stale history rows** — a retained row can name a page an earlier release's apply overwrote. The page authenticates, because the AAD binds no commit id, so `begin_read_at` returned newer bytes with no error. An earlier release can also leave this state on a store whose `Disabled` tag it overwrote. A page's nonce counter now proves it: a page sealed at or after a root of a later commit is newer than the row. `apply_incremental` and `rekey_db` prune that row and every older row, durably, and `begin_read_at` reports `CommitGone` for them. An apply with no delta pages runs no check. `run_deep_walk` and `pagedb-fsck --deep` report the row in the new `DeepWalkReport::stale_history_rows` and change nothing. `is_clean` returns `false` for it. `DeepWalkReport::history_seal_verdict` reports `Inconclusive` when the store cannot show seal order. That covers an epoch above zero, `PlaintextMac`, an observer handle, and a page under another epoch, cipher, or identity. Such a store prunes nothing from this check. On a store that can show order, an apply or a deep walk now reads every page the retained rows reach. These reads skip the cache and include pages the rows share with the live tree. A rekey reads them one more time. The on-disk format does not change. A copy of `main.db` made outside the API that took an apply under an earlier release, then committed as `Standalone`, mixes two counter streams. The check can report and prune an intact row on that copy, or on a snapshot of it. The store cannot show this state. These stay undetectable:
  - A page sealed earlier in the same flush as the later root it is compared against. Flushes run in page-id order.
  - For the newest row, any page sealed before the current live root. A follower holds no root from a commit between its restore and its latest apply.
  - Every row, for good, once a store has an epoch above zero.
  - A page restored to older genuine bytes.
- **Buffer pool budget** — `buffer_pool_pages` and `segment_cache_pages` are now honoured. The cache evicts back to its count after a flush, an abort, or a last unpin. Before, one large transaction kept the pool above budget for the life of the handle. Dirty and pinned pages can still exceed the budget until flushed or released. A large write now misses the cache more often, because the tree no longer stays cached past the budget.
- **Quadratic eviction** — dirty pages leave the eviction list. A large transaction no longer walks them for each clean-page eviction.
- **Lost writes from a racing read** — a read miss that completed after a write replaced the dirty page with older bytes, and a flush could persist them. The resident page now wins. The reads that register no reader cannot run during a swap.
- **Stale file handle** — a read during a compaction or apply swap could keep the replaced file open. Later reads then used the old file.
- **Rekey after an abort** — aborted pages stayed in the cache as clean pages. A rekey could hit one, fail with `ChecksumFailure`, and poison the handle. An abort now removes unpinned dirty pages.
- **Rekey past a torn free page** — a free page that no retained root or reader can name no longer stops a rekey or its resume. A torn page a registered reader can reach still fails, and its bytes stay on disk as evidence. A retained row that reaches a torn page leaves the history instead.
- **`dirty_pages` in `DbStats`** — it counted only one segment id. It now counts every entry.

## [0.1.0] - 2026-10-15

The first stable release. The entries describe `0.1.0` as a whole. The `0.1.0-beta.N` pre-releases have no entries of their own.

### Added

- **B+ tree surface** — sorted `bytes → bytes` with copy-on-write shadow paging, A/B headers, ACID transactions, range scans, monotonic append, and bulk load. Reads return `Bytes` borrowed from the page cache; scans are bounded (`scan_from`, `scan_prefix_from`) or materialising.
- **Segment File API** — engine-owned, append-mostly, atomically sealed encrypted files for formats that own their own layout (vectors, columnar blocks, FTS postings, R-trees).
- **Encrypted pager** — every persistent page is authenticated; AES-256-GCM and ChaCha20-Poly1305 with per-page `cipher_id` for cipher agility. SIEVE page cache with bounded memory budgets.
- **Key hierarchy** — KEK → MK → per-`(realm, file)` DEK/IK, stateful nonce generation with a durable anchor, `zeroize` on all key material.
- **Realm isolation** — `RealmId` bound into AEAD AAD on every persistent page and recorded in the `main.db` header. Per-realm quotas.
- **Cross-platform VFS** — Linux (`io_uring`), Windows (IOCP), macOS/iOS (Grand Central Dispatch), Android, WASM/OPFS and WASI backends, plus a tokio thread-pool fallback and an in-memory backend, with format-bit identity across targets. On Linux the backend is chosen at run time: a kernel that refuses an `io_uring` ring falls back to the thread pool with a warning instead of failing the open. All native backends share one advisory-lock implementation, so processes on different backends still exclude each other on one store.
- **Snapshots** — `snapshot_to`, `restore_from`, and incremental apply, each authenticated against the state its manifest describes. Destinations must be empty; malformed or incomplete artifacts fail closed.
- **Recovery** — open-flow GC, apply-journal replay, deep-walk `fsck`, and the `pagedb-fsck` binary.
- **Online rekey** — rekey under a new key with mixed-cipher and mixed-epoch page coexistence; no full-file migration. A rotation whose source epoch is still pinned by a reader defers retiring it and completes the retirement once the reader set drains — including when the last reader leaves during the deferral itself, so the superseded master key never stays leasable behind an `Ok(())`. A retirement that cannot be taken yet stays queued for the next attempt without holding up the others.
- **Handle modes** — `Standalone`, `Follower`, `ReadOnly`, and `Observer`, each holding its own sentinel. A snapshot or restored directory shares its source's identity, so it opens only as `ReadOnly` or as a `Follower` (`open_follower`, `promote_to_follower`), and a `Standalone` open reports `RestoredNotPromoted`. `rekey_into_writer` forks it into an independent `Standalone` writer under a fresh identity.
- **Open refusals name the parameter, not the store** — `KeyMismatch`, `PageSizeMismatch`, and `RealmMismatch`, each decided before anything is read or written, and none reported as corruption.
- **Failures report themselves** — an unreadable free-list chain, main file, or segment catalog fails `stats()` instead of reporting zero; compaction never skips a catalog entry whose file it cannot open; segment open distinguishes a missing file from a permission or backend error; and only genuine contention is reported as contention. Persisted named-counter rows are validated at open, and commit-history keys are rejected unless exactly eight bytes.

### Security

- Threat model documented in the README; disclosure policy in `SECURITY.md`.
- Data keys are scoped per file, so no two files share a nonce space.
- `io_uring`: an error mid-submission no longer frees a transfer buffer the kernel may still be writing into.
- `pagedb-fsck` requires an explicit KEK — no all-zero default.
- Diagnostic reports redact embedder-chosen segment names.

### Known limitations

- Pre-1.0: the API may break in a minor bump. The on-disk format is frozen for the `0.1.x` line and any later format change ships a migrator — see `VERSIONING.md`. Stores written by a `0.1.0-beta` pre-release are not readable by `0.1.0`.
- pagedb detects tampering, not reversion: an attacker who can write to the store files can substitute an older genuine ciphertext and it will authenticate. Freshness belongs above pagedb.
- `main.db` cannot be reconstructed from `seg/` — back the directory up as a unit.
- Single-writer per database; multi-writer cross-process is not supported.
- Writes carry per-page AEAD and copy-on-write overhead; for throughput-bound plaintext KV workloads a generic store may be faster.
- Applying an incremental snapshot stages a full copy of `main.db` alongside the original, so a follower needs room for two copies during an apply.
